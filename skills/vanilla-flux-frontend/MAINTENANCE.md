# Vanilla Flux Frontend Maintenance

本文约束以后如何把真实项目经验沉淀进 `vanilla-flux-frontend`。

## 维护目标

沉淀"无框架前端怎样写到资深水准"的可迁移判断和最小模板，不是某个项目的实现快照。新增内容前先问：

```text
换一个无框架前端项目，这条规则还成立吗？
它是判断 / 边界 / 模板，还是某个项目的目录、业务名词、颜色值？
它会不会让 skill 变长却不改变判断？
```

## 可以吸收

- 审查中反复出现的问题（例如焦点环被阴影覆盖、`0 &&` 渲染出 0、鉴权前页面的 import 被拦截）：改写成规则或清单项。
- 能直接复用的 core 模板改进（更安全的转义、更清楚的事件类型）。
- 测试、截图验收中的通用误判与规避方法。
- 何时该升级到框架的新判据。

## 不要吸收

- 具体项目的文件路径、id、业务术语、品牌色值、组件清单。
- 一次性的排障过程。
- 与框架项目相关的建议（那属于各框架自己的规范）。

## 结构约定

- `SKILL.md` 只放适用判断、流程、硬性规则和 reference 索引，保持短。
- 细节放 `references/`，在 `SKILL.md` 的 Workflow 里写明何时读哪一份。
- 修改后升级 `version`（规则变化升 minor，措辞修正升 patch），并运行 `check_skill_spec.py` 与 `skills-doctor --no-project`。

## 来源

0.1.0 提炼自一个本地工具型项目的前端改造：先补 Playwright e2e 兜底，再改为 store 单向数据流 + 默认转义模板 + JSDoc strict，再上 design token 视觉体系与全屏预览，最后补纯逻辑单元测试；两轮独立审查发现的问题已写入 `references/review-checklist.md`。

0.2.0 吸收同一项目后续迭代的教训：不静默删减信息（用"显示"选项代替删字段）、固定时区的时间显示、带版本号并校验的 localStorage 偏好、前后端派生值交叉测试、嵌套浮层的 Esc 与菜单裁切、e2e 不依赖异步产出顺序、可调密度的网格与列表。
