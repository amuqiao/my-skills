# 复用 prompt 模板

用户想自己写需求时，给出下面的模板，替换方括号内容即可。装了本 skill 后，最短的说法是："按 vanilla-flux 架构 [新建 / 改造] [项目] 的前端，功能不变 / 新增 [功能]"。

```text
给 [项目/功能] [新建 / 改造] 前端，使用 vanilla-flux-frontend 架构：

【范围】[功能不变，只做工程化和质感升级 / 新增 X 功能]；不改 HTTP API 与数据格式。
【技术约束】原生 ES modules，不引入框架、不加构建步骤；JSDoc + checkJs strict。
【架构】core 层（dom / api / store / ui / types）；共享数据只经 store setter 修改并发事件，
        功能模块订阅后自绘，模块间不互调渲染、无循环依赖；界面状态留在所属模块；
        HTML 只用默认转义的 html 模板；通用行为用 data-* + 全局委托。
【样式】先定 design token（亮暗两套），按钮分级（每区最多一个 primary），应用式铺满布局，
        缩略图可全屏预览，焦点可见、键盘可达。
【测试】纯逻辑放无 DOM 模块写 node:test 单元测试；主流程用 Playwright 离线 e2e（mock，不花钱）。
【流程】先 e2e 兜底 → 工程底座 → 视觉体系 → 逐块换新；每步单独提交且可通过测试；
        截图检查亮暗与宽窄屏；完成后独立 reviewer 只读审查，修完再交付。
【交付】说明改了什么、验证结果、剩余风险；[需要 / 不需要] 提交，不推送。
```

## 让结果更好的写法

1. 改造老项目一定写"功能不变，先加测试兜底"，否则容易边重构边改功能。
2. 点名模式（单向数据流、发布订阅 Store、默认转义模板、design token），比"写规范点 / 高级点"有效。
3. 写清禁止项：不上框架、不要全局可变对象、不要手写 innerHTML、不加静默兜底。
4. 给参照物：指向一个已经按本架构写好的项目目录或架构文档。
5. 要求可验收：类型检查、lint、单元测试、e2e 全过，并附截图。
