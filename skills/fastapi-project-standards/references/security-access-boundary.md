# FastAPI Security Access Boundary

本 reference 用于 FastAPI 接口暴露面、调用主体、凭证、授权/限流和错误暴露的边界判断。它不是安全清单、OWASP 教程、JWT 模板或 API Key 实现手册；它的作用是在创建、审查或重构接口安全时，先判断谁能到达接口、凭什么证明身份、能做什么、失败时暴露什么。

核心问题不是"这个 route 要不要加一个 Depends"，而是：

```text
这个接口暴露给谁，运行在哪个可信边界内？
调用主体是用户、服务、第三方系统、浏览器前端、Webhook 发送方还是运维入口？
凭证证明的是身份、来源、会话还是调用方服务？
认证通过后，还需要哪些资源归属、租户、角色、配额或成本授权？
失败响应和日志会不会泄漏凭证、内部拓扑、供应商信息或请求体敏感内容？
```

## 访问边界心智模型

FastAPI 安全边界从接口暴露面开始，不从某个鉴权库开始。CORS、HTTPS、网关、API Key、JWT、Session、mTLS、限流和错误 envelope 各自解决不同问题，不能互相冒充。

安全设计的目标是减少未授权主体能到达的能力面。先收窄网络和入口，再确认调用主体，再选择凭证，再做授权和限流，最后控制错误与日志暴露。

业务 / 对外 / 跨模块 route 默认不应视为公开接口。公开、匿名、内部、运维、Webhook、health、docs、static、download、stream 等例外必须显式标注访问级别，并能被测试或路由分组检查。新增 route 如果没有安全声明，应按未完成访问边界处理，而不是默认放行。

当模型准备新增或修改接口安全时，先把变化放入下列类别之一：

| 类别 | 含义 | 典型判断 |
| --- | --- | --- |
| `exposure surface` | 接口是否公网、内网、网关后、浏览器可达、Webhook 可达、仅运维可达 | 谁能把请求送到 FastAPI 进程 |
| `caller identity` | 调用主体是用户、租户、内部服务、第三方系统、后台任务还是管理员 | 认证后代表谁 |
| `credential boundary` | API Key、Bearer token、Session cookie、mTLS、网关身份透传、Webhook signature 等 | 凭证证明什么，在哪里校验 |
| `authorization boundary` | 资源归属、租户隔离、角色权限、配额、成本、操作副作用 | 认证通过后是否允许执行 |
| `browser boundary` | CORS、Cookie、CSRF、SSE、WebSocket、前端可见配置 | 浏览器限制和服务端鉴权如何配合 |
| `error/log exposure` | 401/403/429/5xx、错误 details、日志字段、敏感字段脱敏 | 失败时对外和对内分别暴露什么 |

无法分类时，不要直接加依赖、放开 CORS、硬编码 key、扩大错误 details 或记录完整请求体。先说清接口的暴露面和调用主体。

## 暴露面决策门

每个业务 / 对外 / 跨模块接口都应先回答暴露面问题：

- 请求能否从公网到达，还是只在内网、网关、service mesh 或本机脚本中可达？
- 调用方是浏览器用户、后端服务、第三方系统、Webhook 发送方、Worker、CLI 还是运维人员？
- 接口是否暴露高成本能力、写操作、文件/对象访问、长连接、callback、管理能力或调试信息？
- health、metrics、docs、static、download、stream、internal debug 等接口是否有单独边界，而不是默认继承业务接口策略？
- 是否存在代理、网关或负载均衡器注入身份、协议、源 IP 或 request id？
- 新增 route 是否已经声明访问级别；公开或匿名例外是否进入 allowlist、路由分组或等价检查？

内部临时接口也需要最小访问边界。不要把"只在内网"当成无鉴权理由，除非网络边界、调用方集合和失败影响已经明确。

## 调用主体与凭证

先判断调用主体，再选择凭证。不要因为某个凭证实现简单，就反推安全模型。

常见选择原则：

- 单一内部服务调用可以使用服务级 API Key、mTLS 或网关身份，但 key 必须来自配置/Secret，不写死在代码、镜像、测试样例或前端产物。
- 多调用方但无用户系统时，凭证应能区分调用方，便于配额、审计、撤销和轮换。
- 有用户、租户、资源归属或角色权限时，只证明"服务调用方"不够；需要用户/session/JWT 或等价身份，并做资源授权。
- 网关已鉴权时，FastAPI 仍应校验可信透传边界：哪些 header 可信、谁能设置、绕过网关时是否拒绝。
- Webhook 或 callback 入口应校验签名、时间窗口、重放风险和来源身份；不要只靠来源 IP 或 CORS。
- 前端不得持有生产级服务密钥。浏览器可见 token 的权限和生命周期必须按浏览器威胁模型设计。

凭证轮换、过期、撤销和最小权限属于安全合同的一部分。不要把一个长期不变的万能 key 沉淀成项目默认习惯。

凭证配置必须遵守 `configuration-settings.md` 的敏感字段边界：密钥、token、JWT secret、callback secret 和私钥只能作为安全配置语义进入 Settings 或平台 Secret，不应出现在 `model_dump()`、repr、日志、错误响应、OpenAPI 示例、README 示例或测试真实值中。本 reference 只判断凭证语义，不维护配置 key 清单。

## 认证与授权分离

认证回答"是谁"，授权回答"能不能做这件事"。二者不要混在一个 boolean 里。

需要授权判断的典型信号：

- 请求路径、查询参数或 body 中出现用户、租户、caller、资源 id、job id、object key 或文件引用。
- 操作会创建、删除、更新、触发后台任务、调用高成本模型、写外部系统或产生费用。
- 查询结果可能跨用户、跨租户、跨调用方或跨业务包泄漏。
- 同一个调用方对不同 operation、资源、环境或配额有不同权限。

不要相信调用方提交的 `user_id`、`tenant_id`、`caller_id` 或资源归属字段。它们必须与认证身份、网关透传身份、服务端查到的资源 owner 或授权事实源对齐。

401 与 403 的语义应稳定：未认证、凭证缺失或凭证无效是 401；已认证但无权限是 403。不要为了隐藏实现细节把所有安全失败都混成同一个无法排查的错误，除非项目明确有防枚举策略，并在日志中保留可排查分类。

## 限流、配额与成本边界

限流不是鉴权替代品，鉴权也不是成本保护。高成本接口、写操作、文件处理、AI/模型调用、callback 投递、批量查询和长连接都应评估限流或配额。

审查时先判断：

- 限流按谁计数：IP、用户、租户、调用方、API key、operation、资源还是组合维度？
- 失败应返回什么稳定错误语义，是否可重试，是否有 `Retry-After` 或等价提示？
- 队列满、容量保护、配额耗尽和权限不足是否被清晰区分？
- 限流日志是否记录分类和索引，而不是完整请求体、token 或敏感 payload？

不要把内部队列长度、供应商限额、模型名称、密钥状态或基础设施拓扑直接暴露给调用方。

## 浏览器边界

浏览器接入要单独审查。CORS 只控制浏览器是否允许前端读取跨域响应，不证明调用者身份，也不能保护非浏览器客户端。

浏览器相关判断：

- 允许的 origin 是否来自配置或部署边界，而不是 `*` 加凭证。
- Cookie / Session 鉴权是否需要 CSRF 防护、SameSite、Secure、HttpOnly 和过期策略。
- Bearer token 放在浏览器中时，权限、过期时间、刷新和泄漏影响是否可接受。
- SSE / WebSocket / 长轮询是否在连接建立时校验身份，并定义断线、重连、过期和权限变化后的行为。
- 前端能看到的配置只能是公开配置，不包含服务级 key、内部 URL、对象存储签名、callback secret 或管理能力。

不要把 CORS 当鉴权，也不要因为接口只给浏览器页面使用就跳过服务端认证和授权。

## FastAPI 接入位置

FastAPI 中的安全逻辑应放在稳定边界，不要散落在业务函数里临时判断。

- `dependency` 适合解析和校验认证身份、调用方、权限上下文，并把可信主体传给 route / service。
- `middleware` 适合处理 request id、通用 header、跨切面日志和不依赖业务资源加载的全局拒绝；不要在 middleware 中塞租户、角色或资源归属授权。
- 资源归属、租户、角色和配额授权应在 dependency / service 中读取服务端事实源后判断，不要靠解析 path、header 或 body 的自报字段完成。
- `exception handler` 负责把认证、授权、限流和未知错误投影到项目选择的错误合同。
- CORS middleware 只表达浏览器跨域策略，不表达服务端可信身份。
- OpenAPI security scheme 是文档投影，不是事实源；它必须与真实 dependency / middleware 行为一致。

如果项目使用网关、service mesh 或反向代理，FastAPI 侧仍要明确哪些请求头可信、哪些只作为普通用户输入处理。

## 错误与日志暴露

安全失败必须可排查，但对外响应要克制。

对外响应：

- 401、403、429、404、409、5xx 的语义应与项目服务合同一致。
- 错误 message 不应暴露密钥是否存在、token 解析细节、内部服务名、供应商错误、数据库状态或权限规则内部结构。
- 防枚举场景可以把资源不存在和无权限投影为同类 public 错误，但日志中应保留可排查分类。

日志：

- 记录 request id、operation id、调用方摘要、认证/授权失败分类、限流维度和必要资源索引。
- 不记录完整 Authorization header、API key、Cookie、Session、签名、完整请求体、完整响应体、callback secret、signed URL 或可恢复敏感内容。
- token、key、签名、Cookie 出现在异常消息中时，应在记录前分类或脱敏，不能直接 `logger.exception` 带完整上下文。

日志字段细节按 `observability-logging.md` 执行；错误外壳和错误码投影按 `service-contracts.md` 执行。本 reference 只定义安全语义和暴露边界。

## 安全变更审查

当任务新增、修改或删除接口安全逻辑时，先做访问边界审查：

- 暴露面是否变化：公网、内网、网关后、浏览器、Webhook、运维入口？
- 新增或修改的 route 是否有访问级别声明；公开、匿名或运维例外是否显式进入 allowlist、路由分组或等价检查？
- 调用主体是否变化：用户、租户、服务、第三方、后台任务、管理员？
- 凭证是否来自安全配置源，是否支持轮换、撤销、过期或最小权限？
- 认证和授权是否分离，资源归属和租户边界是否由服务端事实源判断？
- CORS、CSRF、Cookie、SSE、WebSocket 是否按浏览器边界处理？
- 限流、配额、成本保护是否与鉴权语义分开？
- 401、403、429、404 和 5xx 是否有稳定错误语义？
- 日志和错误 details 是否没有泄漏 token、密钥、请求体、供应商响应或内部拓扑？

结论不确定时，默认不要扩大暴露面；先保持接口更窄，并把需要用户确认的调用主体和安全承诺说清楚。

## 验证要求

安全规则必须进入测试或机器检查，不能只依赖文档提醒。根据项目规模选择最小可执行检查：

- 未提供凭证、凭证错误、凭证过期或签名错误会被拒绝。
- 所有业务 / 对外 / 跨模块 route 都有访问级别或认证策略声明；公开、匿名、health、docs、static、download、stream 和内部运维例外在 allowlist、路由分组或等价检查中可见。
- 已认证但无资源权限、租户权限、角色权限或配额权限时返回授权失败。
- CORS 配置不把浏览器跨域策略误当成服务端鉴权。
- OpenAPI security scheme 与真实 dependency / middleware 行为一致。
- 日志和错误响应不包含 Authorization、Cookie、API key、secret、完整请求体或敏感 details。
- 高成本或可滥用接口有明确限流、配额或容量保护语义。
- 网关透传身份只在可信边界内接受，绕过网关时不会被普通 header 伪造。

检查失败时应在项目能控制的最早阶段 fail-fast，例如测试、启动、合并或发布前。不要用默认放行、静默降级、万能 key、宽松 CORS 或模糊错误掩盖访问边界问题。
