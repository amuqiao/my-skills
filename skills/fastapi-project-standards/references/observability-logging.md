# FastAPI Observability Logging

本 reference 用于 FastAPI 服务的日志出口、请求追踪、结构化事件、敏感字段边界和日志验证。它不是通用 logging skill，不是日志事件表，也不是项目排障记录；它只沉淀 FastAPI 项目里"什么应该进日志、什么不应该进日志、request_id 由谁负责"这类判断规则。

核心问题不是"这里要不要加一行 logger"，而是：

```text
这条日志是否位于真实排障边界？
它记录的是稳定索引、阶段、分类和规模摘要，还是完整业务数据？
它是否复用了 HTTP 边界确定的同一个 request_id？
它是否把日志误当成业务状态或审计事实源？
日志格式、事件名或敏感字段边界是否有测试约束？
```

## 范围

本 reference 只定义 FastAPI 日志接入和日志内容边界。Metrics、trace、dashboard 和告警平台不属于本文范围；只有在判断"某个信息不该进入日志"时，才需要提到这些相邻系统。

如果项目已经有异步 Job、callback、审计表、对象存储、调用账本或其他事实源，日志应引用它们的稳定索引，不重新定义这些事实源。不要因为新增日志而引入这些机制。

## 日志出口

FastAPI 应用日志默认输出到 stdout/stderr，供容器运行时、K8s 或日志平台采集。应用代码不应默认新增 `logging.FileHandler`，也不应让服务日志只写本地文件。

本地开发需要文件日志时，应由启动脚本、进程管理器或容器平台重定向 stdout/stderr；这是运行形态便利，不是应用日志规则。不要把某个项目的本地日志路径沉淀成通用规范。

Uvicorn access log 只能作为 HTTP 访问摘要，不能替代业务生命周期日志。API 进程和同一服务内的 worker / runtime 入口如果都写服务日志，应复用同一套日志格式、日志级别语义和敏感字段规则。

## Request ID

`request_id` 是单次请求或触发链路的排障关联身份，不是调用方身份、鉴权凭据或幂等键。

HTTP 边界应是 request id 的入口 owner：

- 上游传入合法 request id 时沿用。
- 缺失时生成新的 request id。
- 非法 request id 应返回稳定错误，而不是静默清洗成另一个含义不明的值。
- 最终 request id 应写入请求上下文、日志上下文、响应头和成功/错误 envelope。

Route、Service、Repository、provider adapter 和 worker 不应重新生成另一套 request id。后台任务需要延续 HTTP 触发链路时，应显式传递触发 request id；没有 HTTP 上下文时，使用任务上下文里的稳定关联 id，或使用明确的后台任务占位语义。

不要把 `request_id`、`trace_id`、`job_id` 和 `client_request_id` 混成一个字段。日志可以同时记录这些索引，但不能改变它们原本的合同语义。

## 结构化事件

业务日志事件应有稳定事件名和受控入口，例如事件 registry、枚举、白名单或项目等价机制。新增事件必须经过同一个入口写入，并有测试证明未知事件不会被静默接受。

事件名表达生命周期事实，不表达临时调试句子。优先使用稳定的状态变化或阶段完成语义；不要在不同模块中随手写自由字符串、拼接 event 名或把异常消息当 event 名。

结构化日志字段应保持可机器扫描：

- 使用稳定 key/value 字段，不依赖自然语言句子解析业务状态。
- 字段名应对齐项目已有 API 合同、operation registry、Job 合同或服务内日志字段约定。
- 新增字段前先判断它属于关联索引、生命周期阶段、失败分类、耗时规模，还是完整业务数据。
- `None`、空值、多行文本和异常摘要应有一致处理规则。

不要为了"更详细"记录每个普通 DB 查询、普通字段转换、循环内部小步骤或完整 payload。日志过密会稀释关键路径，也会扩大敏感信息和成本风险。

## 字段边界

适合进入日志的是四类信息：

- 关联索引：request id、operation id、调用方摘要、业务对象 id。
- 生命周期阶段：请求进入/完成、任务开始/结束、外部调用开始/完成、状态迁移。
- 失败分类：错误码、失败阶段、是否可重试、外部依赖名称。
- 耗时与规模：duration、输入条数、文件大小、批次数量、输出对象是否存在。

默认不得记录：

- 密钥、token、签名、cookie、完整连接串密码。
- 完整请求体、完整响应体、完整 callback ack body。
- 完整 prompt、模型原始响应、供应商原始响应。
- 图片、音频、视频二进制、base64 payload、大文件内容。
- signed URL、带 query secret 的 callback URL、内部对象存储地址。
- 身份证明、隐私文本或可直接复原用户敏感内容的字段。

对象 key、URL、hash、输入文本摘要等字段是否可记录，取决于它们是否已经是对外合同的一部分、是否包含可访问凭据、是否能反推出敏感内容。不能确定时，不记录完整值，只记录存在性、大小、类型、稳定 id 或脱敏后的可查索引。

## 记录位置

新增日志前先找排障边界。排障边界通常出现在：

- 请求进入或完成。
- 输入被拒绝、鉴权失败或 header 校验失败。
- 业务状态发生变化。
- 跨进程、跨服务或外部依赖调用。
- 外部副作用发生或被确认。
- 异常被分类，或请求/任务形成终态。

同一事实不要在多个层重复记录。Route 记录 HTTP 事实，Service 记录业务状态变化，Adapter 记录外部依赖边界；不要让每一层都打印同一份 payload 摘要。

## 日志级别

日志级别表达运维语义，不表达代码作者的紧张程度。

| 级别 | 语义 |
| --- | --- |
| `DEBUG` | 本地或临时诊断，不作为生产排障依赖 |
| `INFO` | 正常生命周期关键点和可查询状态摘要 |
| `WARNING` | 可恢复但需要关注的异常路径，例如会重试或触发保护策略 |
| `ERROR` | 当前操作失败并需要排障，例如请求失败、任务终态失败、外部副作用最终失败 |

不要用 `ERROR` 表达已经按设计恢复的瞬时问题，也不要用 `INFO` 打大 payload。异常栈只应留在服务端日志，外部调用方只接收稳定错误 envelope 和 request id。

## 验证

日志规则必须进入测试或机器检查，不能只依赖文档提醒。修改日志出口、日志格式、request id、事件白名单、敏感字段边界或关键业务事件时，至少验证相关不变量：

- 应用日志写向 stdout/stderr，没有默认 `FileHandler`。
- HTTP 请求的 request id 在日志、响应头和 envelope 中一致。
- 非法或缺失 request id 的行为符合 API 合同。
- 结构化事件只能通过 registry、枚举、白名单或等价机制写入，未知事件 fail-fast。
- 新增事件字段不包含完整 payload、密钥、供应商原始响应、signed URL 或隐私文本。
- 后台入口复用相同日志配置，或明确说明它不属于服务日志边界。
- 业务事实仍由项目已有事实源承载，日志只保存索引和摘要。

验证命令按项目选择 targeted tests、contract tests、lint 或服务级验证脚本。不要把某个项目的测试命令作为通用要求；应验证上述不变量确实被覆盖。

## 日志变更审查

当任务新增、修改或删除日志时，先做日志语义审查：

- 这条日志是否位于真实排障边界？
- 事件名是否稳定、受控，并能被测试覆盖？
- 字段是否是索引、阶段、分类或摘要，而不是完整业务数据？
- request id 是否来自统一入口并沿链路传播？
- 日志级别是否匹配运维语义？
- 是否会泄漏密钥、token、prompt、原始响应、signed URL、内部地址或隐私文本？
- 这条日志是否在替代本该由业务事实源、审计、metrics 或 trace 承担的职责？
- 是否有测试或机器检查防止后续漂移？

结论不确定时，默认不要扩大日志面；先记录更小的稳定摘要，并把需要确认的排障目标说清楚。
